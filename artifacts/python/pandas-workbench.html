STEP 3

명령어 실험실

명령어를 하나씩 눌러보세요. 표에서 노랗게 칠해진 게 결과예요. 옆에는 SQL로 쓰면 어떻게 되는지도 같이 보여줘요.

헷갈림 해결: drop([0, 2]) vs iloc[0, 2]

숫자 0과 2는 똑같은데 뜻이 완전히 달라요. 세 표를 나란히 비교해 보세요. 열 번호는 name=0, sex=1, age=2예요.

외우는 법 숫자가 drop( )처럼 함수 괄호 안에 [ ]로 들어가면 목록이에요. iloc[ ]나 loc[ ] 바로 안에 쉼표로 있으면 좌표예요. 그리고 drop은 칸 하나는 못 지워요. 줄 전체나 열 전체만 지워요.
STEP 4

groupby 실험실 = SQL의 GROUP BY

groupby는 "같은 것끼리 바구니에 나눠 담고 → 바구니마다 계산하고 → 결과를 한 표로 합치기"예요. 반 학생들을 반별로 모아서 반 평균 점수를 내는 거랑 똑같아요.

reset_index()를 붙이면 뭐가 달라져?

계산된 숫자는 똑같아요. 바뀌는 건 모양이에요. pclass가 이름표(인덱스)에 있느냐, 보통 열에 있느냐의 차이예요.

① 꺼내는 방법이 달라요

안 붙임r = df.groupby('pclass')['fare'].mean()
r['pclass']    # ❌ 에러! 열이 아니라 이름표라서
r.loc[1]       # ✅ 58.75 (이름표 1번)
r.index        # ✅ [1, 3]
붙임r2 = r.reset_index()
r2['pclass']              # ✅ [1, 3]
r2[r2['pclass'] == 1]     # ✅ 평소 쓰던 불 인덱스
r2.merge(other, on='pclass')  # ✅ 다른 표와 합치기
초보 때 제일 자주 나는 에러 "분명 pclass로 묶었는데 r['pclass']가 왜 없대?" 정답: pclass는 열이 아니라 이름표로 올라가 있어서예요.

③ 그럼 언제 붙여?

그냥 두기결과를 눈으로 보기만 할 때. 더 깔끔하고, r.loc[1]처럼 이름으로 바로 찾을 수 있어요.
reset_index() 붙이기결과를 표로 계속 가공할 때. merge, 새 열 만들기, 차트 x축, SQL처럼 평평한 표가 필요할 때요.
같은 효과# 처음부터 평평한 표로 받기

SQL 번역기: 같은 점 · 다른 점

제목을 누르면 펼쳐져요. 똑같아요는 그냥 번역하면 되는 것, 헷갈림 주의는 SQL 습관대로 쓰면 결과가 달라지는 것이에요.

실행 순서가 달라요

SQL 쓰는 순서
SELECTFROMWHEREGROUP BYHAVINGORDER BYLIMIT
SQL 실제 실행
FROM→WHERE→GROUP BY→HAVING→SELECT→ORDER BY→LIMIT
판다스
df→[조건]→.groupby()→.mean()→[결과 조건]→.sort_values()→.head()

판다스는 쓴 순서 그대로 실행돼요. 왼쪽에서 오른쪽으로 점(.)을 이어 붙이는 게 곧 실행 순서라서, SQL의 실제 실행 순서를 그대로 받아 적는다고 생각하면 편해요.

PANDAS(df[df['age'] > 20]            # WHERE
   .groupby('pclass')['fare']   # GROUP BY
   .mean()                      # SELECT AVG(fare)
   .loc[lambda s: s > 20]       # HAVING
   .sort_values(ascending=False)# ORDER BY ... DESC
   .head(3))                    # LIMIT 3
SQLSELECT pclass, AVG(fare) AS fare
FROM titanic
WHERE age > 20
GROUP BY pclass
HAVING AVG(fare) > 20
ORDER BY fare DESC
LIMIT 3;

조건으로 고르기

불 인덱스불 인덱스(Boolean Index)가 뭐야?

"불"은 불(火)이 아니라 불리언(Boolean) = True/False(참/거짓)예요. 불 인덱스는 True/False 목록으로 줄을 고르는 방법이에요. 두 단계로 일어나요.

1단계 · O/X 목록 만들기df['age'] > 30은 승객마다 "30살 넘어?"에 True/False를 매긴 출석부를 만들어요. 이 목록을 마스크(mask)라고도 해요.
2단계 · True인 줄만 남기기바깥 df[ ]가 그 목록을 받아서 True인 줄만 통과시켜요. 체로 거르는 것과 같아요.

조건을 눌러보세요. 오른쪽 끝 mask 열이 1단계, 흐려지지 않은 줄이 2단계 결과예요.

나눠 쓰기mask = df['age'] > 30   # ① O/X 목록
df[mask]                # ② 고르기

(df['age'] > 30).sum()  # True=1, False=0 → 개수 4
df.loc[df['age'] < 3, 'name']   # 조건 + 원하는 열만
조건 여러 개df[(df['age'] > 30) & (df['sex'] == 'female')]  # AND
df[(df['pclass'] == 1) | (df['fare'] > 20)]      # OR
df[~(df['sex'] == 'male')]                       # NOT
df[df['age'].isna()]                             # 빈칸만
자주 하는 실수 파이썬의 and, or, not 대신 &, |, ~를 써요. 그리고 조건마다 괄호를 꼭 쳐야 해요. 안 치면 계산 순서가 꼬여서 에러가 나요.
꿀팁 True는 1, False는 0으로 계산돼서 .sum()은 조건에 맞는 개수, .mean()은 비율이 돼요. TASK ④에서 survived 평균이 생존율이었던 것도 같은 원리예요.

SQL로는 WHERE예요. SQL은 한 단어로 끝나고, 판다스는 그 속을 열어서 "O/X 목록 만들기 → 고르기"를 눈에 보이게 하는 거예요. 빈칸(NaN/NULL)이 비교에서 빠지는 것도 둘이 똑같아요.

& | ~OR로 했는데 왜 요금 안 넘는 2살 아이가 뽑혀? 그리고 ~는 뭐야?

실수가 아니에요! |(OR)는 두 조건 중 하나만 True여도 통과예요. Palsson은 요금 조건은 못 넘었지만 나이 조건(10살 미만)을 만족해서 들어왔어요.

주의 1 · 괄호 df[~df['sex'] == 'male']은 ❌. ~가 ==보다 먼저 계산돼서 "sex 열을 뒤집어라"가 돼버려요. isin(), isna()처럼 함수로 끝나는 건 그 자체가 한 덩어리라 괄호 없이도 돼요.
주의 2 · not은 안 돼요 파이썬 not은 True/False 하나만 뒤집어요. 판다스 조건은 True/False가 여러 개 든 목록이라 ~를 써요.

괄호 문법

괄호df['fare'] vs df[['fare']] 대괄호 두 겹은 왜 표야?

바깥 [ ]는 "골라줘"라는 명령이고, 안쪽 [ ]는 파이썬 리스트(목록)예요. 이름 하나를 주면 열 하나(시리즈)가 오고, 목록을 주면 "이 열들로 된 표"(데이터프레임)가 와요. 목록에 하나만 들어 있어도 표로 와요.

🥤

"콜라 주세요"라고 하면 캔 하나를 손에 쥐어줘요(시리즈). "콜라 담은 봉투 주세요"라고 하면 캔 하나가 든 봉투를 줘요(데이터프레임). 내용물은 같고 받는 모양만 달라요.

실무실무에선 항상 평평한 표(reset_index)로 바꾸는 게 좋아?

원본 지키기

SQLDELETE FROM titanic;이랑 WHERE 있는 거랑 뭐가 달라?

WHERE는 "어떤 줄을?"을 정하는 조건이에요. 없으면 SQL은 "조건 없음 = 전부"로 알아들어요.

SQLDELETE FROM titanic WHERE age IS NULL;  -- 나이 빈칸인 줄만 (Moran 1명)
DELETE FROM titanic WHERE pclass = 3;   -- 3등석만 (5명)
DELETE FROM titanic;                    -- 조건 없음 → 8명 전부!
🏫

DELETE FROM 우리반 WHERE 지각 = 1;은 "지각한 사람만 나가세요"예요. DELETE FROM 우리반;은 "다 나가세요". 표 껍데기(열 이름)만 남고 안은 0명이 돼요. WHERE를 빼먹는 실수가 가장 유명한 사고예요.

판다스에는 "지워라"가 아니라 "남길 줄만 고른다"고 생각해요. 그래서 조건을 뒤집어서 써요.

PANDASdf[df['pclass'] == 3]   # WHERE pclass = 3 → 3등석만 고르기
df[df['pclass'] != 3]   # 3등석을 "지운" 결과 = 나머지만
df.iloc[0:0]            # 전부 지운 것 = 열 이름만 있는 빈 표
SQLSELECT * FROM titanic WHERE pclass = 3;
DELETE FROM titanic WHERE pclass = 3;
DELETE FROM titanic;

SQL에서 행 거르기

SQL"행은 조건으로" 때문에 WHERE가 행을 거르는 거야?

네, 정확해요! SQL은 처음부터 그 원칙대로 자리를 나눠서 만들어졌어요.

SELECT = 열 고르기이름으로 불러요. SELECT name, fare
WHERE = 행 고르기조건으로 걸러요. WHERE age > 30

그래서 WHERE에는 "3번째 줄" 같은 줄 번호를 쓸 수 없어요. SQL 표에는 줄 번호나 이름표가 없어서 언제나 "이 조건을 만족하는 줄"로만 골라요.

SQL에서 행을 고르는 자리언제 거르나기준판다스
WHERE묶기 전 원본 줄조건df[df['age'] > 30]
HAVINGGROUP BY로 묶은 후 결과 줄조건r[r > 20]
LIMIT정렬한 뒤 맨 위에서개수.head(3)
(없음)아무 때나이름표 · 번호df.loc[3], df.iloc[2]
헷갈림 주의평균 요금 거르기를 왜 WHERE가 아니라 HAVING에서 해?

순서 때문이에요. WHERE가 실행되는 순간에는 아직 평균이라는 게 존재하지 않아요. 아래 그림은 이 쿼리가 실제로 흘러가는 순서예요.

SQLSELECT pclass, AVG(fare)
FROM titanic
WHERE age > 20            -- ① 승객 한 명씩: 20살 넘는 사람만
GROUP BY pclass           -- ② 남은 사람을 등급별 바구니로
HAVING AVG(fare) > 20;    -- ③ 바구니마다 평균 → 20 넘는 바구니만
FROM→WHERE→GROUP BY→HAVING→SELECT→ORDER BY→LIMIT
WHERE 시점표가 아직 승객 한 줄 한 줄이에요. 각 줄엔 그 사람의 나이·요금뿐이라 "1등석 평균"은 물어볼 수가 없어요.
HAVING 시점바구니를 나누고 평균을 계산한 다음이에요. 이제 "1등석 58.75, 3등석 7.74"가 있으니 비교할 수 있어요.
🏆

반 평균 비유 "반 평균 70점 넘는 반만 상 주자." 철수가 65점이어도 철수네 반 평균은 75점일 수 있어요. 학생 한 명만 봐서는 알 수 없죠. 반별로 모으고 → 평균 내고 → 그다음에 반을 골라야 해요. WHERE는 학생 한 명을, HAVING은 반 하나를 판단해요.

에러SELECT pclass, AVG(fare) FROM titanic
WHERE AVG(fare) > 20     -- ❌ WHERE에선 집계 함수 금지
GROUP BY pclass;
PANDASr = (df[df['age'] > 20]       # WHERE
       .groupby('pclass')['fare'] # GROUP BY
       .mean())
r[r > 20]                         # HAVING
# pclass
# 1    58.75

판다스는 쓴 순서대로 실행돼서 "평균 낸 다음 거른다"가 코드 모양 그대로 보여요. SQL은 쓰는 순서와 실행 순서가 달라서, 묶기 전 거르기(WHERE)와 묶은 후 거르기(HAVING)를 다른 단어로 나눠 놓은 거예요.

SQL 사투리

SQL"MEDIAN은 DB마다 이름이 달라요"가 무슨 말이야?

SQL은 표준 언어지만 MySQL, PostgreSQL, SQLite, Oracle, BigQuery 같은 데이터베이스 프로그램마다 "사투리"가 있어요. 같은 영어라도 미국은 elevator, 영국은 lift라고 하는 것처럼요. 다른 단어를 쓰면 에러가 나요.

데이터베이스중앙값 쓰는 법
Oracle, Snowflake, DuckDBMEDIAN(age)
PostgreSQL, SQL ServerPERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY age) ("50% 지점 값")
BigQueryPERCENTILE_CONT(age, 0.5) OVER ()
MySQL, SQLite함수가 없음 → 정렬해서 가운데를 직접 찾는 긴 쿼리
어디서나 같음SELECT WHERE GROUP BY ORDER BY COUNT SUM AVG MIN MAX COALESCE. 처음 배우는 기본기는 대부분 여기예요.
사투리가 갈림중앙값 같은 통계 함수, 날짜 함수, 문자열 함수, 위에서 n개 자르기(LIMIT 3가 SQL Server에선 SELECT TOP 3)

SQLBolt 같은 브라우저 연습 사이트는 보통 SQLite 기반이라 MEDIAN을 쓰면 에러가 날 거예요. 판다스는 프로그램이 하나뿐이라 어디서나 df['age'].median()이에요.

특강 · 제일 헷갈리는 것

이건 열이야? 행이야? 값이야?

번역 사전을 보면 판다스도 SQL도 거의 다 열 이름으로 일을 해요. 그럼 리스트 [ ]는 항상 열일까요? 정답은 "아니요"예요. 이 섹션 하나로 헷갈림을 끝내봐요.

① 리스트는 봉투예요. 방향이 없어요

리스트는 그냥 "여러 개를 담은 봉투"예요. 봉투 자체는 열도 행도 아니에요. 어느 우체통에 넣느냐에 따라 열이 되기도, 행이 되기도, 값이 되기도 해요.

코드리스트의 뜻왜?
df[['name', 'fare']]열그냥 df[ ]에 글자를 넣으면 열 이름으로 읽어요
df.iloc[[0, 2]]행iloc 쉼표 앞자리 = 행 자리
df.drop([0, 2], axis=0)행axis=0 = 행 방향 (기본값)
df.drop(['age', 'fare'], axis=1)열axis=1 = 열 방향
df['name'].isin(['Allen', 'Moran'])값열은 이미 df['name']으로 정해졌으니 괄호 안은 찾을 내용
df.groupby(['sex', 'pclass'])열"~열로 묶어줘"라는 함수
df.sort_values(by=['age', 'fare'])열"~열 기준으로 정렬해줘"라는 함수
열이 많이 나오는 건 리스트 때문이 아니에요. 그 함수가 원래 열을 받는 함수라서 그래요. 똑같은 리스트를 iloc이나 drop(axis=0)에 넣으면 행이 돼요.

② 그래도 "열 중심"인 이유: 열은 이름으로, 행은 조건으로

열은 이름으로 불러요열은 수가 적고 이름과 뜻이 있어요(age, fare, sex). 그래서 이름을 직접 불러요. 설문지의 "질문 항목"이에요.
행은 조건으로 골라요행은 수가 많고 이름보다 내용이 중요해요. 891명을 하나하나 부르는 대신 "30살 넘는 사람"처럼 골라요. 설문지에 "응답한 사람들"이에요.

그래서 행을 고를 때도 결국 열 이름이 등장해요. 아래 코드는 age 열을 쓰지만, 결과로 골라지는 건 행이에요.

PANDASdf[df['age'] > 30]   # 기준은 age 열, 골라지는 건 행
SQLSELECT * FROM titanic WHERE age > 30;
판다스만의 차이 SQL은 행을 조건으로만 골라요. 표에 정해진 순서나 이름표가 없거든요. 판다스는 행에 인덱스가 있어서 loc[3], iloc[2]처럼 이름이나 번호로도 부를 수 있어요.

③ 제일 헷갈리는 df[ ]의 네 얼굴

그냥 df[ ]는 안에 뭘 넣느냐에 따라 열을 고르기도, 행을 고르기도 해요. 판다스가 편하라고 만든 지름길인데, 그래서 헷갈려요.

헷갈리면 loc을 쓰면 확실해요. loc[행, 열]처럼 자리가 고정돼서 쉼표 앞은 언제나 행, 뒤는 언제나 열이에요. 
PANDASdf.loc[df['age'] > 30, ['name', 'fare']]   # 30살 넘는 사람(행)의 name, fare(열)

질문 1대괄호 바로 앞이 loc / iloc?그럼 자리로 정해져요. loc[ 행 , 열 ]. 쉼표가 없으면 행이에요.
